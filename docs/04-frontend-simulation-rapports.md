# Step 5 — Frontend on real data, what‑if simulator, reports

> Working notes. They will be merged into the final README.

## 1. From daily data to a "live" dashboard: the replay

The Excel data is **daily**. A supervision screen must look alive, so the backend **replays**
the 335 real days like a video: **1 real day = 60 seconds** (`ECOENERGY_REPLAY_SECONDS_PER_DAY`).

`GET /api/live` returns the state "now":

| Kind of value | How it is made | `source` |
|---|---|---|
| Production, consumption, purchases, steam, water flows | real daily total ÷ 24 → average rate (MWh/j ÷ 24 = MW) | `real` |
| Specific consumption, autonomy, availability | computed from real values | `computed` |
| VHP pressure/temperature, condensate temperature, air pressure, steam per CAP line | **simulated** inside the plant's target ranges (sine over the day + noise, seeded per 2 s tick) | `simulated` |

Rules: when GTA3 is stopped, turbine sensors return `null` (no invented values). The UI shows
a violet **SIMULÉ** badge on every simulated value. `?day=2025-03-29` pins a day (demo).

Later, real sensors (IoT, MQTT/OPC‑UA) can replace the replay **without changing the frontend**:
it only knows `/api/live`.

## 2. Frontend architecture

| File | Role |
|---|---|
| `lib/api.ts` | The only place that talks to the backend. TypeScript types mirror `schemas.py`. SWR hooks: `useLive` (every 2 s), `useSeries`, `useKpis`, `useMeta`, `useSimModel`, `useSimulation` |
| `components/scada/ui.tsx` | Shared pieces: `Panel`, `KpiTile`, `StatCard`, `PeriodPicker`, `ChartTooltip`… |
| `components/scada/data-source.tsx` | `SimBadge`, `ReplayChip`, `ApiError` (clear message if the backend is down) |

**SWR** = "stale‑while‑revalidate": shows the last data immediately, refetches in the
background, and shares one request between components asking for the same URL.

Missing days are drawn as **gaps**, never interpolated: a line across the March–April
shutdown would suggest data that doesn't exist.

The Production page used to have start/stop buttons for the units. A supervision prototype
must not pretend to control a real plant (in industry, control goes through the DCS/SCADA with
safety interlocks), so it became a monitoring page.

## 4. The what‑if simulator (fitted on real data)

### Research
- **Willans line**: steam consumption of a steam turbine is almost linear in its power output
  (classic engineering model).
- **Extraction turbine**: steam extracted at low pressure (BP) for process heat doesn't expand
  down to the condenser, so it produces less power.
- **Morocco grid emission factor**: 0.60 tCO₂/MWh (IEA).
- **ONEE very‑high‑voltage tariff**: ~0.48 (off‑peak) to ~0.75 DH/kWh (peak).

### Fit on 224 days where GTA3 ran ~24 h
```
P (MW) = 0.65 + 0.1505 × VHP (t/h) − 0.0186 × BP (t/h)     R² = 0.966, mean error 0.26 MW
VHP (t/h) = −3.63 + 7.27 × P (MW)                           Willans line, R² = 0.964
```

### Cross‑checks with independent facts
| Check | Result |
|---|---|
| Willans slope 7.27 t/MWh | inside the plant's own target 6.8–7.5 |
| BP coefficient | negative, as physics predicts |
| Mass balance BP + condensate | 99.7 % of VHP |
| Price actually paid | 670 DH/MWh, inside the ONEE tariff range |

### Model
- steam admitted = min(available, turbines × 90 t/h) — 90 t/h = daily‑report target 2160 t/j
- BP extraction ≤ steam admitted; condensate = admitted − BP
- purchases = max(0, consumption − production); cost = purchases × 24 × price
- warnings: specific consumption or condensate outside target, wasted steam, outside the
  domain observed in 2025 (extrapolation)

### Scenarios (from the data)
| Scenario | Production | Autonomy | Savings vs median day |
|---|---|---|---|
| Median day 2025 | 10.7 MW | 51 % | — |
| CAP at 70 % (less BP) | 11.05 MW | 53 % | ≈ 2 M DH/year |
| GTA2 back in service + median MC steam | ≈ 15.9 MW | ≈ 76 % | **≈ 30 M DH/year** |

The GTA2 scenario assumes the turbine is repaired and MC steam is available: it gives an
order of magnitude to justify a decision, not a promise.

Tests (`tests/test_simulator.py`): the fit recovers known coefficients from synthetic data,
mass and power balances hold, turbine capacity limits steam, impossible inputs → 422.

## 5. Reports (PDF and Excel)

`GET /api/reports/{id}.{pdf|xlsx}?start=&end=` builds the file on demand from the cleaned data.

| Report | Content |
|---|---|
| Synthèse | all KPIs + production/consumption chart |
| Bilan énergétique | electricity KPIs, purchases per tariff period, availability |
| Traitement des eaux | WDS, destinations, reagents, fire network |
| Production et vapeur | ACP, bill per tonne, specific consumption vs target band |
| Qualité des données | every value removed by the pipeline and why |

- **Excel** (openpyxl): "Synthèse" sheet (KPIs), "Données journalières" (header with units,
  frozen), "Colonnes" (Excel source of each column).
- **PDF** (fpdf2 + matplotlib): KPI table + chart. DejaVu font so that "→", "³", "₂" and
  accents print correctly.
- KPIs come from the **same function** as `/api/kpis`, so the PDF, the Excel and the dashboard
  always show the same numbers.
- `Content-Disposition: attachment` makes the browser download the file.
